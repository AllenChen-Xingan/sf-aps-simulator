# STRESS-ABS reporting checklist

This document maps each item of the STRESS-ABS checklist for agent-based simulation (Monks et al., 2019; item wording as applied by Taylor et al., 2018) to the place in this package where it is reported. Each entry gives a short answer and a pointer; the pointed-to section is authoritative.

| Section | Item | Recommendation (abridged) | Where reported | Summary |
|---|---|---|---|---|
| **1. Objectives** | 1.1 Purpose of the model | Background and rationale | `ODD+D.md` §1.1; `TRACE.md` §1.1–1.3 | Compares seven funding and coordination pathways for converting San Francisco's pending APS requests into funded installations, under six alternative explanations of the observed stall. A rule-based simulation is used because funding events are too few for statistical estimation while the governing rules are documented. |
| | 1.2 Model outputs | System-level outputs emerging from agent interactions | `ODD+D.md` §4.13; `experiment-protocol.md` §5.3 | Installations within five and ten years, whether a request-channel batch award occurs within five years, time to the first award, pathway nodes reached. Experiments aggregate these into robustness (share of parameter combinations in which a pathway installs more than current practice over ten years) and funding within five years. |
| | 1.3 Experimentation aims | Research questions answered | `TRACE.md` §1.2; `experiment-protocol.md` §5 | Which pathways outperform current practice across uncertain conditions; under what conditions money flows; which uncertain inputs most influence outcomes. |
| **2. Logic** | 2.1 Base model overview diagram | State chart, process flow or equivalent | `ODD+D.md` §3.1, §3.3 (decision-flow diagram) | Monthly nine-step sequence and an overall decision-flow diagram with each node mapped to a code function. |
| | 2.2 Base model logic | Logic in text, including intermediate calculations | `ODD+D.md` §3, §8 | Every submodel is given as pseudocode or an equation with its function name and line numbers in `code/model.py`. |
| | 2.3 Scenario logic | Differences between base case and scenarios | `ODD+D.md` §8.12–8.15; `experiment-protocol.md` §4, §9.3 | Seven pathways (PW0–PW6) with start actions and switching rules, each in a decision table; six settings (M-A to M-D) switch mechanisms on or off; the approval variant changes how PW4 and PW5 obtain a local line. |
| | 2.4 Algorithms | Algorithms mimicking real processes | `ODD+D.md` §8.6–8.9 | HSIP benefit–cost calculation, bundling under the agency ceiling, the pedestrian set-aside, eligibility review and approval. |
| | 2.5.1 Environment | Structure of the environment | `ODD+D.md` §2.7–2.8 | No spatial environment; agents interact through rule-based funding venues (HSIP rounds, Prop L, General Fund, existing signal projects) on a monthly calendar. 76 pending crossings plus new arrivals, each with its own crash record, cost category and routes. |
| | 2.5.2 Agents | Agents, attributes and decision rules (data used, objectives, rules, groups, prediction) | `ODD+D.md` §2.1–2.6, §4.2–4.11 | One decision-making agent (SFMTA capital-budget and grant staff) deciding monthly whether to start an application (logistic rule in `ODD+D.md` §8.2); rule-following actors (engineering staff, Signal Shop, advocates, enforcement bodies). No learning or prediction. |
| | 2.5.3 Interaction topology | With whom, selection, frequency, concurrency | `ODD+D.md` §4.6, §3.1 | Interactions are fixed by role: requests to engineering staff; pressure and enforcement to the deciding agent; applications to venues; awards to crews or contractors. Events within a month follow the fixed sequence of §3.1. |
| | 2.5.4 Entry/exit | Creation and removal of agents | `ODD+D.md` §8.1, §8.11 | New requests arrive as a Poisson process; crossings leave the waiting list when installed; terminated projects return crossings to their pre-award status. |
| **3. Data** | 3.1 Data sources | All data sources | `data-dictionary.md`; `actors-and-evidence.md`; `references.md` | SFMTA request-status lists 2020–2026, signal inventory, DataSF injury-crash records, capital plans, Prop L documents, Caltrans HSIP instructions and award lists, disability-council proceedings, one interview with SFMTA staff. |
| | 3.2 Input parameters | Each parameter, description and values | `data/parameters.csv`; `parameters.md` | 98 parameters with range, default, unit, active settings, source category and source. |
| | 3.3 Pre-processing | Data manipulation before use | `data-dictionary.md`; `code/data_prep.py`, `code/build_inputs.py` | Matching requests to signal identifiers and crash records; deduplication; classification into status groups. |
| | 3.4 Assumptions | Justification where data are unavailable | `parameters.md` §3; `actors-and-evidence.md`; `TRACE.md` §3.4 | Quantities without documentary values are sampled over ranges and covered by sensitivity analysis; source category is recorded for every parameter. |
| **4. Experimentation** | 4.1 Initialisation | Warm-up and initial conditions | `ODD+D.md` §6; `TRACE.md` §6 | No warm-up. A historical segment from July 2022 is used to screen parameter combinations against recorded request lists; projections start from the June 2026 waiting list. |
| | 4.2 Run length | Run length and time units | `ODD+D.md` §2.8; `experiment-protocol.md` §5 | Monthly steps; projections of 120 months from July 2026; historical segment of 48 months. |
| | 4.3 Estimation approach | Deterministic or stochastic; replications | `experiment-protocol.md` §3; `ODD+D.md` §4.12 | Stochastic. 20 replicates per parameter combination, 1,000 Latin-hypercube combinations per setting, common random numbers across pathways. |
| **5. Implementation** | 5.1 Software | Operating system, language and versions | `environment/python-version.txt`; `environment/requirements-lock.txt`; `reproducibility.md` | Python with pinned dependencies (NumPy, pandas, SALib, EMA Workbench, scikit-learn); runs on any OS with that interpreter. |
| | 5.2 Random sampling | Random number generation | `experiment-protocol.md` §3; `code/runner.py` | NumPy generators seeded through `SeedSequence` from a master seed and a task label; results do not depend on the number of worker processes. |
| | 5.3 Model execution | How time is modelled | `ODD+D.md` §3 | Fixed monthly time steps with a fixed within-month order; scheduled events (rounds, budget windows, deadlines) are checked each month. |
| | 5.4 System specification | Run time and hardware | `reproducibility.md` | Reported with the hardware, process count and wall-clock time of each experiment. |
| **6. Code access** | 6.1 Computer model sharing statement | Where code and results are available | `README.md` | Code (MIT licence), documentation and data (CC BY 4.0), checksums in `SHA256SUMS`, one-command reproduction with `reproduce.sh`. |
